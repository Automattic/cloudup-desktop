# Desktop App Update Process

How the Cloudup desktop app receives updates, and how to publish new releases.

## Overview

There are two systems:

1. **Legacy (cloudup-osx)**: Objective-C macOS app using Automattic's private `AutoUpdate.framework`. Updates are hosted on `updates.cloudup.com` and published via the [cloudup-releases](https://github.com/Automattic/cloudup-releases) GitHub repo + a systems request. The legacy system also served Windows releases (via the same `cloudup-releases` repo), though the Windows desktop app is no longer actively maintained.

2. **New (Electron desktop app)**: Uses `electron-updater` pointed at GitHub Releases. Requires a new **public** GitHub repository to host release artifacts. Not yet publishing releases.

## Legacy App (cloudup-osx)

### How the client checks for updates

The app uses [Automattic/auto-update](https://github.com/Automattic/auto-update/) (`AutoUpdate.framework`), linked as a git submodule. The framework's Cocoa port lives in `AutoUpdate.Cocoa/` in the auto-update repo and provides the `AUUpdater` class that handles update checking, downloading, and installation. The app-side configuration and update installation policy is implemented in `UpdateHelper.m`, which acts as the `AUUpdaterDelegate`.

On launch, the app:
1. Reads preferences from `NSUserDefaults`:
   - `updateHost` — default `updates.cloudup.com`
   - `updateChannel` — default `release` (also supports `dev`)
   - `updatePercentile` — random 1–100, seeded once per install (for staged rollouts)
2. Creates an `AUUpdater` instance with those settings
3. Calls `checkForUpdates` immediately. `AUUpdater` internally re-checks on a default interval (every 4 hours). In `dev` channel, `UpdateHelper.m` overrides this to 60 seconds via `_updater.interval = 60`

Updates can be disabled with the `CLOUDUP_DISABLE_UPDATES` environment variable.

### Update installation logic

When an update is available, `UpdateHelper` decides when to install:

- **Critical updates**: install immediately
- **Non-critical updates** are deferred if:
  - The app is marked busy (e.g. uploading — set via `cloudup.setBusy(true)` from JS)
  - The panel is visible
  - The About window is open
  - Release channel and app has been running < 5 minutes

When conditions are met, the app sets an `updated` flag, terminates, and calls `installUpdate`. On next launch, a notification shows the new version and release notes.

### Update channels

Switch channels with macOS `defaults`:

```bash
# Production (default)
defaults write com.cloudup.Cloudup updateHost -string "updates.cloudup.com"
defaults write com.cloudup.Cloudup updateChannel -string "release"

# Internal/QA (uses the "release" channel on the internal update server)
defaults write com.cloudup.Cloudup updateChannel -string "release"
defaults write com.cloudup.Cloudup updateHost -string "updates-internal.cloudup.com"

# Dev channel (faster check interval)
defaults write com.cloudup.Cloudup updateChannel -string "dev"
```

Or use Makefile targets: `make release-channel`, `make qa-channel`, `make dev-channel`.

### Update manifest format

The `AutoUpdate.framework` expects a JSON manifest at the update server. Generated by `scripts/BundleApp.sh`:

```json
{
  "app": "Cloudup",
  "version": "1.15.5-1259",
  "channels": ["dev", "release"],
  "entries": [
    {
      "os": "osx",
      "architectures": ["x86-64"],
      "osversion": " >= 10.6 ",
      "appversion": "*",
      "path": "Cloudup-1.15.5-1259-osx.tar.gz",
      "format": "gz"
    },
    {
      "os": "osx",
      "architectures": ["x86-64"],
      "osversion": " >= 10.6 ",
      "appversion": "*",
      "path": "Cloudup-1.15.5-1259-osx.zip",
      "format": "zip"
    }

}
```

### Publishing a legacy release

#### Prerequisites

- Xcode + command line tools
- Node.js with `npm install -g js` (CLI for inline JS evaluation, used by `BundleApp.sh`)
- Apple Developer ID signing certificate (see [fieldguide](https://fieldguide.automattic.com/app-signing-certificates/))
- Apple ID with app-specific password for notarization
- Membership in the A8C Apple developer group

#### Build steps

```bash
cd cloudup-osx

# 1. Update submodules (cloudup-local + auto-update)
git submodule init && git submodule update

# 2. Build and sign
./scripts/Release.sh
# - Say NO when prompted to move to Applications
# - Allow keychain access when prompted for codesigning

# 3. Notarize (will prompt for Apple ID credentials)
./scripts/notarize.sh

# 4. Staple notarization ticket
./scripts/staple.sh

# 5. Generate archives and manifest JSON
./scripts/BundleApp.sh

# 6. Tag the release in git
./scripts/tag-release.sh
```

#### Upload to cloudup-releases

The [cloudup-releases](https://github.com/Automattic/cloudup-releases) repo hosts the release artifacts. Directory structure uses **major.minor version** with an `x` patch suffix:

```
cloudup-releases/
├── 1.14.x/
│   ├── Cloudup-1.14.0-1237-osx.tar.gz
│   ├── Cloudup-1.14.0-1237-osx.zip
│   └── Cloudup-1.14.0-1237-osx.json
├── 1.15.x/
│   ├── Cloudup-1.15.4-1246-osx.tar.gz
│   ├── Cloudup-1.15.4-1246-osx.zip
│   ├── Cloudup-1.15.4-1246-osx.json
│   ├── Cloudup-1.15.5-1259-osx.tar.gz
│   ├── Cloudup-1.15.5-1259-osx.zip
│   └── Cloudup-1.15.5-1259-osx.json
└── ...
```

So versions `1.15.4` and `1.15.5` both go in `1.15.x/`.

Steps:

1. Clone the releases repo: `git clone git@github.com:Automattic/cloudup-releases`
2. Create the version directory if needed (e.g. `1.15.x/`)
3. Copy the `.tar.gz`, `.zip`, and `.json` files from `cloudup-osx/build/`
4. If reusing a directory, copy the JSON from the previous release and update the version/paths
5. Create a PR and get team review
6. Once merged, post to **+systemsrequests** asking them to publish the update

The systems team deploys the files to `updates.cloudup.com` where `AutoUpdate.framework` can find them.

## Migrating Users from Legacy to Electron App

Existing users only have the legacy `AutoUpdate.framework` as their update channel. The transition to the Electron app must be delivered as a one-time update through the legacy system. After that, `electron-updater` takes over for all future updates.

### How it works

`AutoUpdate.framework` replaces the `.app` bundle in-place. It doesn't care what's inside the bundle — it downloads the archive, extracts it, and swaps the old `Cloudup.app` with the new one. This means we can package the Electron-built `Cloudup.app` in the legacy archive format and push it through `updates.cloudup.com` like any other legacy release.

```
┌─────────────────┐
│  Legacy app     │
│  (Obj-C)        │
│  AutoUpdate.fw  │
└────────┬────────┘
         │
         │  legacy update
         │  via updates.cloudup.com
         ▼
┌─────────────────┐
│  Electron app   │
│  v1.0.0         │
│  (first install)│
└────────┬────────┘
         │
         │  electron-updater
         │  via GitHub Releases
         ▼
┌─────────────────┐
│  Electron app   │
│  v1.1.0+        │
│  (all future)   │
└─────────────────┘
```

### Bundle ID change

The legacy app uses bundle ID `com.cloudup.Cloudup`. The Electron app uses `com.automattic.cloudup`. This change has consequences:

- **NSUserDefaults**: Non-sensitive preferences (auto-launch, update channel, UI state) stored under `com.cloudup.Cloudup` can be migrated on first launch via `defaults read com.cloudup.Cloudup <key>` (or the `node-defaults` npm package) and written into `electron-store`. Set a "migrated" flag so the app doesn't re-read stale values on subsequent launches. Auth tokens are **not** stored in NSUserDefaults — do not attempt to migrate credentials this way.
- **Keychain items**: Credentials stored under the old bundle ID are not accessible to an app with a different bundle ID under the hardened runtime. Users will need to re-authenticate after the transition.
- **Login items**: If the legacy app is set to launch at login, the login item references the old bundle ID. The Electron app will need to register its own login item; the old one becomes a dangling reference that macOS will silently ignore.
- **Notification Center**: Notification permissions are per bundle ID. The Electron app will need to request permission separately.

### Steps to publish the transition update

1. **Build the Electron app** for production:
   ```bash
   # (repo root)
   npm run dist:mac
   ```
   This produces `release/Cloudup-{version}-arm64.dmg` and `release/Cloudup-{version}-arm64.zip`.

2. **Extract the `.app` bundle** from the build output:
   ```bash
   # The .app is inside the DMG or can be found in release/mac-arm64/
   ```

3. **Package in legacy format** — create the archives and manifest that `AutoUpdate.framework` expects:
   ```bash
   # Archive as .tar.gz
   tar -czf Cloudup-{version}-osx.tar.gz Cloudup.app

   # Archive as .zip
   zip -r Cloudup-{version}-osx.zip Cloudup.app
   ```

4. **Create the legacy JSON manifest**:
   ```json
   {
     "app": "Cloudup",
     "version": "{version}",
     "channels": ["dev", "release"],
     "entries": [
       {
         "os": "osx",
         "architectures": ["arm64"],
         "osversion": " >= 10.13 ",
         "appversion": "*",
         "path": "Cloudup-{version}-osx.tar.gz",
         "format": "gz"
       },
       {
         "os": "osx",
         "architectures": ["arm64"],
         "osversion": " >= 10.13 ",
         "appversion": "*",
         "path": "Cloudup-{version}-osx.zip",
         "format": "zip"
       }
     ]
   }
   ```
   Note: The Electron app is currently arm64-only. To support x86-64 for the transition, configure a universal build in `electron-builder.yml` and update the `architectures` array above to include `"x86-64"`.

   The legacy system also served Windows users via `cloudup-releases`. There is no transition path documented for Windows legacy users. If there are active Windows legacy app users, they will not receive the transition update unless a Windows Electron build is also published through the legacy release mechanism. The Electron app's `electron-builder.yml` already includes a Windows (NSIS, x64) target, but no legacy Windows update bridge is planned.

5. **Upload to cloudup-releases** following the standard legacy process:
   - Add files to the appropriate `major.minor.x/` directory
   - Create a PR for review
   - Once merged, post to **+systemsrequests** to publish

6. **Verify the transition**:
   - Install the current legacy app
   - Wait for or trigger an update check
   - Confirm the Electron app launches after the update
   - Confirm `electron-updater` is active and checking for future updates

### Rollout strategy

Given the risks of a full app replacement, use the legacy percentile system for staged rollout:

1. **Dev channel first**: Publish to the `dev` channel only. Test internally.
2. **Small percentile on release**: Set `channels` to `["release"]` but rely on the percentile system to limit initial exposure. Internal testers can set their percentile low with `defaults write com.cloudup.Cloudup updatePercentile -integer 1`.
3. **Full rollout**: Once validated, publish without percentile restrictions.

### Rollback plan

If the Electron app has critical issues after the transition update:

- Push a new legacy-format update through `updates.cloudup.com` with a patched Electron build
- The Electron app's `electron-updater` can also deliver fixes independently via GitHub Releases, but only to users who already transitioned
- There is **no automated way to revert to the Objective-C app** once the transition update is installed — the legacy `AutoUpdate.framework` code is no longer running

## New Electron App (this repository)

### Current auto-update implementation

The Electron app in this repository uses `electron-updater` (v6.7.3). The update logic is in `src/main/updater.ts`:

- Only active when `ENV === 'production'`
- Auto-downloads updates in the background
- Auto-installs on app quit
- Shows a native notification when an update is downloaded
- Checks on startup and every 4 hours

### What a release contains

Each GitHub Release must include these assets, all generated automatically by `electron-builder`:

| Asset | Purpose |
|-------|---------|
| `Cloudup-{version}-arm64.dmg` | macOS installer (drag-to-Applications) |
| `Cloudup-{version}-arm64.zip` | macOS ZIP (used by `electron-updater` for differential updates) |
| `latest-mac.yml` | Update manifest — `electron-updater` reads this to detect new versions |

The `latest-mac.yml` file is critical. It contains the version, file names, sizes, and SHA-512 checksums. Example:

```yaml
version: 1.0.0
files:
  - url: Cloudup-1.0.0-arm64.zip
    sha512: <base64-encoded-sha512>
    size: 12345678
  - url: Cloudup-1.0.0-arm64.dmg
    sha512: <base64-encoded-sha512>
    size: 23456789
path: Cloudup-1.0.0-arm64.zip
sha512: <base64-encoded-sha512>
releaseDate: '2026-03-11T12:00:00.000Z'
```

`electron-updater` compares the version in `latest-mac.yml` against the running app version. If newer, it downloads the ZIP and applies the update.

### Automated release pipeline

Releases should be automated via CI. The current Buildkite pipeline (`.buildkite/`) already builds and signs the app but uses `--publish never`.

**To enable automated releases:**

> **Warning**: Do not enable `--publish always` until step 1 is complete. The current config points to a private repo where `electron-updater` cannot fetch releases.

1. **Create the public releases repo** on GitHub
2. **Update `electron-builder.yml`** to point to the new repo
3. **Add a publish step to CI** that runs on tagged commits:
   ```bash
   # Instead of --publish never:
   npx electron-builder --mac --publish always
   ```
   This makes `electron-builder` create a GitHub Release and upload all assets including `latest-mac.yml`.
4. **Configure a `GH_TOKEN`** in CI with write access to the releases repo
5. **Tag-based workflow**: Push a version tag (e.g. `v1.0.0`) to trigger the release pipeline

**Recommended release flow:**

```
1. Bump version in package.json
2. Commit and push to trunk
3. Tag the commit: git tag v1.0.0 && git push origin v1.0.0
4. CI detects the tag → builds, signs, notarizes, publishes to GitHub Releases
5. electron-updater on user machines picks up the new release within 4 hours
```

### Testing releases before publishing

Before enabling automated publishing:

1. **Test locally**: Run `npm run dist:mac` and verify the DMG installs and runs correctly
2. **Test update flow**: Create a draft GitHub Release manually with the built assets. Install an older version, point it at the draft release, and confirm the update downloads and installs.
3. **Test `latest-mac.yml`**: Verify the manifest is well-formed and checksums match the artifacts
4. **Staged rollout**: Use the `stagingPercentage` field in `latest-mac.yml` to roll out to a subset of users initially

### Additional work needed

- **Staged rollouts**: The legacy app uses a percentile system. `electron-updater` supports this via the `stagingPercentage` field in `latest-mac.yml`.
- **Busy/visible guards**: Port the legacy behavior where updates are deferred during uploads or when the UI is active. The current implementation installs unconditionally on quit.
- **Code signing & notarization**: Already handled by Fastlane in `.buildkite/` and `fastlane/Fastfile`.
